# Maestro

Take the request all the way: decide it, build it, prove it, and hand the user a pull request that can merge through the repository's landing procedure.

## How we work

Ask first whether to hold it or let it merge when green. Keep approvals and consequential product decisions with the user. Throughout this Maestro invocation, talk and write plainly and concisely, and define each technical term when first used. This plain-language rule belongs to Maestro; it does not make [bro](../bro/SKILL.md) persistent.

Use [start](../start/SKILL.md) to take on the work. The isolated worktree and branch are always created before edits, and the repository's gates and landing procedure are read from its own authorities.

## Discover

Run [discover](../discover/SKILL.md) with the user. When [improve](../improve/SKILL.md) hands over an accepted and verified scan, treat that scan as completed discovery and do not repeat it. If the scan settled behavioral decisions beyond the original candidate, use [spec](../spec/SKILL.md) to synthesize them. Otherwise carry the agreed candidate and criteria verbatim as the behavioral baseline. Then continue to the Plan. Discovery first explains what the request means in this repository, then sizes the unknowns work to the task.

After discovery, tell the user how much of the remaining process the work needs. Skip a nonmandatory phase only when nothing in it is unclear and a wrong call would be cheap to reverse after merge. If the work grows, go back to and re-enter the skipped phase.

When discovery ends, use [spec](../spec/SKILL.md) only when discovery settled something the original request did not already say. Carry the resulting spec, including its acceptance criteria and named test interfaces, into architecture, every builder brief, QA, and review. When discovery settled nothing beyond the request, carry the request text verbatim as the spec. The spec is a run artifact and review input. It does not open or mutate a tracker issue by itself.

## Set the direction and write the Plan

The root task writes a durable Plan before builders start, separate from the spec or verbatim request. Use [architect](../architect/SKILL.md) only when design, acceptance criteria, domain terms, consequential interfaces, or independent slices still need settling; its decisions contribute to the Plan, and its shared module vocabulary comes from [codebase-design](../codebase-design/SKILL.md). When that work is already settled or trivial, skip Architect and write the shortest sufficient Plan. Use the repository's authorized planning location; when none exists, keep the Plan in isolated run state or the conversation. Never create or mutate a tracker item merely to publish it.

The Plan fixes what builders must not decide: domain meaning, ownership, invariants, complete consequential interfaces and failure behavior, allowed dependency and control flow, trust boundaries and irreversible effects, any threat-model sentence, the named test interfaces, and independent vertical slices with exact file ownership and dependencies. Each slice is a narrow but complete path through every layer it needs. The Plan also names what a builder may change freely and the evidence review will inspect.

Before any builder starts, freeze the neutral boundary facts: target and base, architectural owner boundary, relevant sibling surfaces, public, security, and product contracts, changed-file and exact slice file bounds, non-test LOC measurements, named test interfaces, and the exact threat-model sentence when relevant. For review, the changed-file and slice bounds and LOC are measurements and evidence, never hard scope caps; for builder isolation, the Plan's exact slice file ownership remains binding. Keep the Spec behavioral baseline separate: the spec or verbatim request plus the violated invariant and intended behavior when applicable. Standards receives the neutral facts plus trusted frozen-base authority and never receives the request, specification, violated invariant, or intended behavior. Spec receives the same neutral facts plus that behavioral baseline.

Every run has four invariants: an isolated worktree and branch, green project gates, the whole diff reviewed for bugs and read against the spec, and a pull request. Each other phase states its own condition where it runs:

- The Plan names the fewest and highest interfaces the work's tests cross. Each builder brief names its test surfaces, and review receives those names. If the work adds a check, gate, or validator, include one threat model sentence naming the input or actor class it covers and what it deliberately excludes. A qualifying architecture decision writes an ADR in the repository's decision home in the same diff, including the verdict it reverses when it reverses one.
- Use [panel](../panel/SKILL.md) only when a decision is open, costly to reverse, and cannot be settled by a test, prototype, repository evidence, or a standard solution.
- Use [use-claude](../use-claude/SKILL.md) when a poor design would be costly to reverse after merge. Give Claude Fable 5 at high effort the discovery, spec, architecture, and proposed execution for a read-only second opinion. When reversal is cheap, state that the cross-read is skipped.
- Then use [orchestrate](../orchestrate/SKILL.md) once the direction, behavioral baseline, Plan, and slices are clear. Give each builder [implement](../implement/SKILL.md), the inputs it needs, and the repository's quality gates. The main run worktree remains the integration worktree. Before dispatching a multi-builder run, create one distinct slice branch and worktree per independent slice from the frozen integration base. Each builder edits only its slice worktree, so parallel builders never share Git state. Before integration, review each completed slice by invoking the trusted sanitized [code-review](../code-review/SKILL.md) helper on that slice branch against the frozen integration base at P2 with streamed output and the one high-reasoning engine selected in its builder dispatch, never the integrated fixed panel. Before trusting that engine's first clean slice result, run the malicious smoke harness with the exact selected engine, model, and thinking configuration. Run the Standards and Spec reviews as applicable against that same slice before integration. Integrate only the accepted slice commit into the main run worktree. With one builder, it may use the main run worktree and skip its slice review only when the integrated structured review will run.
- On the integrated diff, dispatch one fresh high-reasoning native Codex review worker to run [code-review](../code-review/SKILL.md) whole. Give it the frozen target and base, neutral boundary facts, separate Spec behavioral baseline, and project commands. The worker gives the Standards review the neutral facts plus trusted frozen-base authority and no behavioral input. It gives the Spec review the same neutral facts plus the spec or verbatim request, violated invariant, and intended behavior when applicable. The review worker is a leaf: it verifies and classifies routine findings, returns accepted repair briefs and a review record to the root task, and never spawns a builder or edits production code. The root task decides that record and escalations and never edits production code. It dispatches accepted repairs to builders under [implement](../implement/SKILL.md), then sends the repaired head back to the same review worker for affected proof and the complete dual-panel, Standards, and Spec reviews. The Standards and Spec reviews run in parallel, following Bottega `e0926de`. A finding whose fix changes the promised contract returns to the user. After two review-triggered repair cycles without convergence, the root task pauses and reclassifies every remaining finding. It continues only when every remaining accepted finding is an in-scope blocker and the cycles are narrowing; otherwise it returns the scope decision to the user or records a follow-up.
- Run an independent architecture read after review when the design would be costly to reverse. Give a fresh native Codex subagent the architecture and [architect](../architect/SKILL.md), blind to the review record, and ask it to apply the architect review questions to the integrated diff. Keep the reports separate and decide each finding. The same reader rechecks accepted repairs. When an architecture finding drives a repair, re-enter [panel](../panel/SKILL.md) if that changed decision meets its conditions, then return the repaired head through the complete dual-panel, Standards, and Spec reviews before proceeding.
- When a user-facing surface or product behavior changed, use [qa](../qa/SKILL.md). Judge every required scenario against the spec and any approved prototype render. Triage failures as one batch and send accepted repairs through [implement](../implement/SKILL.md). Any change after the first accepted review, including a review, architecture, or QA repair, returns through every required review. After the final reviewed SHA is accepted, rerun the complete required QA scenario set, never only an affected subset, so all review and QA evidence names that SHA. A scenario still failing after two QA repair rounds returns to the root task for a decision. When no user-facing surface or product behavior changed, skip QA and state that it was skipped.
- Use [close](../close/SKILL.md) after the accepted head, its gates, review reads, and any required QA all point to one SHA.

Make repository-answerable and cheaply reversible decisions during the run. State the choice and the reason, then keep moving. The user retains approvals, consequential product choices, rule exceptions, irreversible actions, and review fixes that would change the promised contract. A revision that adds a new requirement returns to the user before any builder starts. When that new requirement adds a check, gate, or validator, ship its threat model sentence before the user reviews it. Keep working on independent work while waiting for a user-owned answer.

If a worker fails, diagnose the failure before retrying it once. If the user says stop, stop active workers cleanly, preserve completed work, and stop.
